Day 01. 프로젝트 문서의 역할과 연결 이해하기

같은 “회의실 예약 서비스”를 만들기로 했는데 한 사람은 예약 버튼만, 다른 사람은 회의실 목록만 생각하고 있다면 어떨까요? 코드를 잘 작성해도 서로 연결되지 않는 결과물이 나올 수 있습니다.

이번에는 프로젝트 문서가 무엇을 정하고 누구의 다음 작업을 돕는지 살펴봅니다. 수업은 서비스 기획에서 데이터·API 설계로 이어지고, 마지막에 설계를 보완해 발표합니다. 예습에서는 문서의 역할과 연결을 이해합니다. 완성된 제출물 작성이나 문법·구현은 수업에 남깁니다. 이 글은 첫날에 읽고, 3일 동안 기획과 설계를 진행하며 함께 참고하는 공통 예습 자료입니다.

지난 수업 복습

앞선 웹·API 수업에서 화면의 입력을 서버에 보내고 결과를 돌려받는 흐름을 만났습니다. 코드 작성법을 기억하지 못해도 괜찮습니다. 오늘은 그 코드를 나눠 만들기 전에 무엇을 서로 맞춰야 하는지 봅니다.

오늘 수업에서 꼭 가져가야 할 것

같은 서비스를 만드는 사람들이 서로 다른 것을 만들지 않으려면, 무엇을 문서로 맞춰야 할까요?

문서는 제출용으로 길게 쓰는 설명문만이 아닙니다. “누구를 위한 기능인가”, “무엇을 입력하는가”, “실패하면 어떻게 되는가”를 함께 결정하고, 구현과 확인의 기준으로 다시 찾아보는 기록입니다. 문서마다 보는 관점은 다르지만 같은 기능을 설명해야 합니다.

상세 설명

1. 서비스의 목적과 기능부터 맞춘다

강의안의 회의실 예약 예시를 빌려 봅시다. 화이트보드에 적던 예약을 웹에서 확인하고, 사용자가 원하는 시간을 예약할 수 있게 하려는 상황입니다. 여기서는 같은 회의실의 같은 시간대에 예약이 겹치면 새 예약을 받지 않는다는 규칙을 따라가겠습니다. 아래의 이름·ID·문서 조각은 이해를 위한 축약 예시이며 제출 정답이 아닙니다.

명세

서비스 개요는 누구의 어떤 문제를 왜 해결하는지 정합니다. “여러 사람이 예약 현황을 함께 확인하기 어려우므로, 웹에서 회의실별 예약을 확인하게 한다”가 예입니다. 서비스를 제안하는 사람과 만드는 사람 모두 이 목적을 보고 기능이 필요한지 판단합니다. “예약 서비스입니다”라는 이름만으로는 해결할 문제나 범위를 알기 어렵습니다.

액터별 요구사항은 그 목적을 실제 행동과 규칙으로 나눕니다. 관리자는 회의실 정보를 관리하고, 사용자는 예약을 조회하거나 추가합니다. 한 사람이 때에 따라 두 역할을 맡을 수도 있습니다. 액터인 “사용자”와 문서를 읽는 “화면 개발 담당자”는 다른 구분입니다. 전자는 서비스를 쓰는 역할이고, 후자는 서비스를 만드는 일의 역할입니다.

API

프로그램 사이에서 어떤 기능을 어떤 방식으로 요청하고 결과를 받을지 정한 접점과 약속.

요청

다른 프로그램에 처리해 달라고 보내는 메시지.

응답

요청을 받은 프로그램이 돌려주는 처리 결과 메시지.

예약 한 번의 흐름은 다음과 같습니다.

  1. 화면에서 회의실과 시간 등을 선택해 예약 요청을 보냅니다.
  2. 서버는 기존 예약과 겹치는지 확인하고, 가능하면 예약을 저장합니다.
  3. 서버가 성공 또는 실패 응답을 돌려주면 화면은 결과를 보여 줍니다.

API 명세는 이때 어떤 요청과 응답을 주고받을지 설명하는 문서입니다. 명세를 작성했다고 서버가 구현되거나 예약이 저장되는 것은 아닙니다. 화면에서 예약된 시간을 선택하지 못하게 해도 서버의 확인이 필요합니다. 화면을 연 뒤 다른 사람이 먼저 예약할 수 있기 때문입니다. 동시에 도착한 요청까지 안전하게 처리하는 구현은 여기서 다루지 않습니다.

UI 흐름도

사용자의 행동에 따라 화면이나 화면 상태가 어떻게 이어지는지 나타낸 그림.

와이어프레임은 한 화면 안에 무엇이 있는지, UI 흐름도는 그 화면들이 어떻게 이어지는지를 보여 줍니다. 실무에서 두 내용을 한 문서에 함께 담을 수도 있지만 역할은 구분해 읽어야 합니다.

예약 화면에는 회의실·날짜·시간을 고르는 곳과 예약 버튼이 필요합니다. 버튼을 누르면 회의명과 예약자를 입력하게 하고, 성공하면 예약 현황을 다시 보여 주기로 정할 수 있습니다. 실패하면 입력을 유지한 채 다른 시간을 고르도록 안내할 수도 있습니다.

여기서 “할 수도 있다”는 부분은 팀이 결정할 설계입니다. 화면 그림에 버튼만 놓지 말고 눌렀을 때의 행동과 표시할 데이터도 적어야 합니다. 화면 담당자는 이것을 보고 무엇을 만들지 알고, 서버 담당자는 어떤 정보가 필요한지 확인합니다. 테스트 담당자는 사용자가 실제로 예약을 끝낼 수 있는지 따라가 봅니다.

예를 들어 화면에는 종료 시각 입력창이 있는데 요구사항에는 시작 시각만 있다면, 누가 임의로 채우기 전에 예약 길이를 어떻게 정할지 먼저 합의해야 합니다. 그림을 그리는 과정에서 요구사항의 빈틈을 발견할 수 있는 것입니다.

ID는 대상을 구별하는 식별자입니다. 회의실 이름이 같거나 나중에 바뀌더라도 어느 회의실인지 구분할 수 있도록 “회의실 R-101” 같은 값을 사용합니다. 실제 API 명세에는 요청 주소와 방식, 필수 항목·자료형·오류 표현도 구체적으로 정합니다. 자료형은 숫자나 문자열처럼 값의 종류입니다. 예습에서는 문법을 외우기보다 호출하는 쪽과 처리하는 쪽이 같은 약속을 읽는 문서라는 점을 잡으세요.

데이터 모델은 서비스에 필요한 기록과 그 관계를 정합니다.

예약의 회의실 ID를 보고 어느 회의실의 예약인지 연결합니다. 회의실 하나에는 서로 다른 시간의 예약이 여러 개 연결될 수 있습니다. 이것이 일대다(1:N) 관계의 예입니다. 단, 같은 시간의 중복 예약은 별도 규칙으로 막아야 합니다. 관계에 선 하나를 그렸다고 모든 업무 규칙이 자동으로 지켜지는 것은 아닙니다.

서버·데이터 담당자는 이 모델을 보고 저장과 조회 구조를 구현합니다. 화면 담당자도 필요한 정보의 근거가 있는지 함께 확인할 수 있습니다. 다만 API 응답은 데이터베이스 한 행을 그대로 복사한 것이 아닐 수 있습니다. 예약 현황 응답에 회의실 이름을 포함하려면 회의실 기록을 함께 조회해 조합할 수 있습니다. 화면에 표시하는 값이 모두 독립된 저장 항목이어야 하는 것도 아닙니다. 계산해서 보여 주는 값이라면 어떤 기록과 규칙으로 계산하는지 설명하면 됩니다. 서로 일치해야 한다는 뜻은 모양을 똑같이 만들라는 것이 아니라, 필요한 정보를 빠짐없이 설명하라는 뜻입니다.

5. 한 기능을 끝까지 따라가며 문서 사이의 빈틈을 찾는다

화면실패 이유를 보여 주고 사용자가 다른 시간을 고를 수 있다
API중복 때문에 실패했다는 결과를 클라이언트에 전달한다
데이터·처리회의실과 예약 시간을 확인할 기록이 있고, 중복을 검사할 수 있다

요구사항에는 중복을 막는다고 적었는데 API 문서에는 성공 결과만 있다면, 화면 담당자는 실패했을 때 무엇을 받을지 알 수 없습니다. 이처럼 문서들을 연결해 읽으면 한 문서만 볼 때 놓친 빈틈이 보입니다.

기능이 바뀔 때도 같은 방식으로 확인합니다. 예를 들어 예약할 때 참석 인원을 받기로 했다면, 요구사항에 왜 필요한지와 조건을 적고, 화면 입력·API 요청·저장 여부·오류 상황이 함께 맞는지 살핍니다. 이미 같은 정보가 있거나 계산할 수 있다면 모든 문서를 기계적으로 고치는 대신 영향받는 부분을 확인하고 결정 이유를 남깁니다.

실제 프로젝트에서는 이런 내용을 한 파일, 여러 파일, 협업 도구의 페이지나 이슈에 나눠 담을 수 있습니다. 이슈는 팀이 할 일이나 문제를 기록하고 논의하는 항목입니다. 모든 문서를 한 번 완성한 뒤 영원히 고정하는 것이 아닙니다. 구현하거나 확인하다 발견한 사실을 반영하고, 누가 무엇을 바꿨는지 서로 알 수 있게 관리합니다. 문서 수보다 중요한 것은 현재 합의가 어디에 있는지와 실제 동작이 그 합의와 맞는지입니다.

6. 이번 수업의 제출물은 역할을 묶어 담는 그릇이다

강의안에서는 다음 세 종류의 파일을 제출합니다. 앞에서 다룬 다섯 가지 관점이 각각 별도 파일이라는 뜻은 아닙니다.

옆으로 밀어서 비교 →
제출 파일담는 내용과 역할
프로젝트 기술서 PDF서비스 개요·배경·액터별 기능·UI 흐름으로 무엇을 만들고 어떻게 쓸지 설명
API 명세서 YML화면과 서버가 주고받을 요청·응답을 정해진 형식으로 기록
DB 다이어그램 DBML저장할 데이터와 관계를 도구가 읽을 수 있는 형태로 기록

OpenAPI Specification(OAS)은 HTTP API를 설명하는 표준입니다. HTTP는 웹에서 요청과 응답을 주고받을 때 사용하는 통신 규칙입니다. YAML은 구조가 있는 데이터를 글자로 표현하는 형식이며, .yml은 그 파일 확장자입니다. OpenAPI가 설명의 규칙이라면 YAML은 그 내용을 적는 표현 형식입니다. Swagger Editor는 이런 API 명세를 작성·확인하는 도구로 수업에서 만납니다. DBML은 데이터베이스 구조를 텍스트로 기술하는 언어입니다. ERD가 관계를 보는 그림이라면 DBML은 그 모델을 기술하는 방법 중 하나입니다. 파일을 만들었다고 실행 중인 서버나 데이터베이스가 만들어지는 것은 아닙니다.

이번 과제는 UI 흐름을 PDF 안에 포함하도록 요구합니다. 파일 이름과 마감은 강의안의 제출 지침을 확인하세요. 과제에서 API의 Security Schemes, 즉 인증 방식 등을 기술하는 항목을 제외한다고 해서 실제 서비스에서 보안을 고려하지 않아도 된다는 뜻은 아닙니다. 이 예습은 인증·권한 설계나 안전한 구현을 완료한 자료가 아닙니다.
