FastAPI 모델 서빙

Day 01. 학습한 모델이 요청을 받아 답하기까지

예정 강의일 · 2026.09.30

감자 품질 선별 연구소에 무게를 예측하는 모델이 생겼습니다. 이제 검사 화면에서도 그 모델의 답을 받아 보고 싶습니다. 모델 파일을 화면 옆에 복사하면 끝날까요? 어느 프로그램이 입력을 받고, 모델을 준비하고, 결과를 돌려줄지 정해야 합니다.

이번 3일 수업은 모델을 요청에 연결하고, 교체할 버전을 관리하고, 운영 상태를 확인하는 흐름입니다. 오늘은 요청이 들어와 예측 응답이 나가기까지의 역할을 읽습니다. FastAPI 서버 전체 구현과 성능 측정은 수업에서 이어갑니다.

예시는 합성 배치 P-0930입니다. 먼저 영상에서 얻은 표면적과 품종으로 무게를 추정하고, 저울 실측은 나중에 평가에 쓰는 설명용 상황입니다. 앞 과목의 출고 여부 분류와는 다른 회귀 문제이며, 실제 장비의 효율이나 예측 성능을 주장하는 사례는 아닙니다.

추론

학습 때 품종을 숫자로 바꾸거나 입력 크기를 조정했다면, 새 감자를 추론할 때도 그때 정한 처리 규칙이 필요합니다. 새 요청마다 모델을 다시 학습하거나 새 평균을 구하는 것은 아닙니다. 이 관계를 서비스에서도 유지하는 것이 출발점입니다.

오늘 수업에서 꼭 가져가야 할 것

학습한 모델이 다른 프로그램의 요청을 받아 답하려면 무엇이 필요할까요?

모델을 사용할 프로그램, 입력과 출력의 약속, 배운 모델과 전처리 규칙이 필요합니다. 입력이 약속에 맞는지 확인하고, 처리할 준비가 되었는지 살핀 뒤, 결과 또는 오류를 돌려줍니다. 점수가 좋은 모델을 얻는 일과 요청을 안정적으로 처리하는 일은 이어져 있지만 확인할 대상이 다릅니다.

1. 모델 파일을 서비스로 연결한다

서빙

학습한 모델을 실제 입력에 사용할 수 있도록 제공하는 일. serving이라고 합니다.

아티팩트

학습이나 빌드 뒤 저장해 다시 사용할 결과물. 여기서는 모델 파일과 함께 보관한 전처리 정보 등이 해당합니다. artifact라고 합니다.

모델 파일에는 배운 값과 구조 등이 저장됩니다. 파일이 있다는 사실만으로 검사 화면의 요청을 받을 수는 없습니다. 실행 중인 프로그램이 파일을 읽어 사용할 준비를 하고, 요청의 입력을 모델에 전달해야 합니다. 파일을 읽어 메모리에 준비하는 일을 모델 로딩(loading)이라고 합니다.

API

프로그램끼리 기능을 사용하고 자료를 주고받기 위해 정한 약속.

요청

상대 프로그램에 처리해 달라고 보내는 메시지. request라고 합니다.

응답

요청에 대해 돌려주는 처리 결과 메시지. response라고 합니다.

연구소의 검사 화면이 클라이언트이고, 무게 예측 기능을 제공하는 프로그램이 서버입니다. 서버는 약속한 입력을 받아 모델로 추론하고, 클라이언트가 읽을 수 있는 형태로 결과를 보냅니다. API는 창구의 약속에, 요청은 한 번의 처리 부탁에 해당합니다. 이 비유가 서버가 사람 한 명처럼 한 번에 한 일만 한다는 뜻은 아닙니다.

검사 화면 → 요청 → 입력 검사 → 학습 때 정한 전처리 → 모델 추론 → 응답 → 검사 화면

강의의 감성 분류 예시는 문장을 받아 긍정·부정 등의 범주와 점수를 돌려줍니다. 감자 예시는 특징을 받아 무게를 돌려줍니다. 입력과 모델은 달라도 모델 앞뒤에 요청과 응답을 연결한다는 구조는 같습니다. 두 예시가 같은 데이터나 모델은 아닙니다.

http://localhost:8000/predict라는 주소를 나누어 봅시다. http는 통신 방식, localhost는 그 주소를 사용하는 프로그램이 실행 중인 자기 컴퓨터, 8000은 포트, /predict는 서버 안에서 찾을 경로입니다. 다른 사람의 컴퓨터에서 localhost를 열면 연구소 서버가 아니라 그 사람의 컴퓨터를 가리킵니다.

HTTP 요청에는 주소 외에도 메서드(method)라는 행동 구분이 있습니다. 이 예에서는 GET /health로 상태를 조회하고 POST /predict로 예측할 자료를 보냅니다. GET과 POST라는 단어가 예측 알고리즘의 종류를 뜻하지는 않습니다.

엔드포인트

API에서 요청할 기능을 구분하는 접점. 여기서는 HTTP 메서드와 경로의 조합으로 읽습니다.

라우팅

요청의 메서드와 경로를 처리할 함수에 연결하는 일.

예측 요청의 본문에는 다음과 같은 JSON을 담을 수 있습니다. 본문(body)은 메시지에 실어 보내는 자료 부분입니다. 중괄호 안에서 콜론 왼쪽은 항목의 이름인 키(key), 오른쪽은 값(value)입니다. 120은 숫자이고, 따옴표 안의 수미는 문자열입니다.

{
  "surface_area_cm2": 120,
  "variety": "수미"
}

서버가 돌려줄 응답 모양의 합성 예시는 다음과 같습니다. 180은 실제 모델을 실행한 결과가 아닙니다. request_id는 나중에 같은 요청을 찾을 식별자이고, model_version은 어느 모델 버전이 답했는지 알려 줍니다.

{
  "request_id": "P-0930-001",
  "predicted_weight_g": 180,
  "model_version": "v1"
}

요청에는 표면적과 품종을 넣었고 응답에는 예측 무게가 담겼습니다. 저울로 잰 실제 무게는 아직 없으므로, 이 응답만으로 오차가 몇 g인지 알 수는 없습니다.

3. FastAPI는 모델 앞뒤의 약속을 연결한다

낯선 말 4개눌러서 뜻 보기
스키마

자료에 어떤 항목과 자료형, 조건이 있어야 하는지 정한 구조. schema라고 합니다.

FastAPI

Python으로 웹 API를 만들 때 라우팅과 요청·응답 처리 등을 제공하는 프레임워크.

Pydantic

선언한 자료형과 조건에 맞게 데이터를 해석하고 검증하는 Python 도구.

Uvicorn

FastAPI 같은 앱을 실행해 웹 요청을 받도록 하는 서버 프로그램.

FastAPI는 무게 예측 규칙을 학습해 주는 모델 자체가 아닙니다. 어떤 요청을 어떤 함수에 보낼지 연결하고, Pydantic으로 표현한 입력·출력 구조를 사용합니다. Uvicorn은 이 앱이 실제로 웹 요청을 받게 실행합니다. 프레임워크는 자주 필요한 기능과 구조를 제공하는 틀이라고 이해하면 됩니다.

스키마에는 surface_area_cm2가 양수인 숫자여야 한다거나 variety가 허용한 품종 이름이어야 한다는 조건을 정할 수 있습니다. 이때 말하는 자료형(type)은 숫자·문자열처럼 값의 종류입니다. Pydantic의 ‘모델’은 이런 자료 구조를 선언하는 뜻이며, 데이터에서 무게를 배운 머신러닝 모델과는 다른 말입니다.

형식 검사를 통과했다고 올바른 입력이라는 보장은 없습니다. cm²로 배운 모델에 다른 단위의 숫자를 보내도 양수 조건은 통과할 수 있습니다. 특징의 의미·순서·단위, 품종을 바꾸는 규칙까지 학습 때와 맞아야 합니다. 스키마 검사와 학습·서빙 사이 입력 처리의 일치는 서로 다른 확인입니다.

코드에서 라우팅은 이런 모습으로 만납니다. 아래는 연결을 읽기 위한 조각이며 app을 만드는 부분을 생략했으므로 그대로 실행할 완성 서버가 아닙니다.

@app.get("/health")
def health():
    return {"status": "ok"}

함수(function)는 이름을 붙인 처리 묶음입니다. def health():는 health라는 함수를 정의하고, 들여쓴 줄이 그 함수가 할 일입니다. return은 결과를 돌려줍니다. 중괄호는 여기서 Python의 딕셔너리, 즉 키와 값을 짝지은 자료이며 JSON과 표기가 비슷하지만 같은 언어는 아닙니다. FastAPI가 이를 응답으로 변환합니다.

앞의 @app.get("/health")는 /health로 들어오는 GET 요청을 아래 함수와 연결하는 표시입니다. @로 붙이는 이런 표시를 데코레이터(decorator)라고 합니다. 그 내부 구현보다 이 경로의 요청이 이 함수를 실행한다는 관계부터 읽으면 됩니다.

FastAPI는 선언한 구조를 바탕으로 OpenAPI라는 형식의 API 명세를 만들고, 기본 /docs 경로의 Swagger UI에서 명세를 보고 요청을 시험할 수 있게 합니다. 문서가 생겼다는 사실이 모델의 정확성이나 모든 오류 처리를 검증했다는 뜻은 아닙니다.

실행 중 일어난 일을 나중에 확인할 수 있도록 남긴 기록. log라고 합니다.

잘못된 입력은 추론 전에 걸러야 합니다. 선언한 요청 조건을 어기면 FastAPI의 기본 검증에서는 보통 422 응답으로 문제가 있는 항목을 알려 줍니다. 앱이 별도로 정한 잘못된 요청에는 400을 사용할 수도 있습니다. 처리 중 서버 내부에서 문제가 생긴 경우는 500 같은 서버 오류와 구별합니다. 오류 처리(error handling)는 실패를 발견하고 알맞은 응답과 기록으로 다루는 일입니다.

200 응답은 HTTP 처리가 성공했다는 뜻입니다. 예측 무게가 실제 무게와 맞다는 뜻은 아닙니다. 반대로 모델의 평가 점수가 좋더라도 파일을 읽지 못하면 예측 요청을 정상적으로 처리할 수 없습니다.

앞 코드처럼 언제나 ok를 반환하는 /health는 함수가 응답한다는 것만 보여 줍니다. 모델이 실제로 로딩됐는지까지 검사하려면 그 조건을 코드에 넣어야 합니다. 프로그램의 생존 여부와 지금 예측을 받을 준비가 되었는지를 나누어 보는 이유입니다. healthy라는 문자열만으로 모든 상태가 확인되는 것은 아닙니다.

모델 로딩에는 두 시점이 있습니다. Eager Loading은 시작 과정에서 모델을 미리 준비하고, Lazy Loading은 처음 필요할 때 준비합니다. 전자는 준비 시간이 시작에, 후자는 첫 요청에 더해질 수 있습니다. 둘 중 하나가 항상 빠르다는 결론보다 ‘사용자가 기다리는 시점이 어디인가’를 봅니다. 메모리와 준비 상태도 함께 고려합니다.

요청 식별자, 처리 시각, 모델 버전, 상태 코드 같은 로그를 남기면 어느 요청에서 무슨 일이 있었는지 되짚을 수 있습니다. 기록을 계속 보관하려면 파일이나 데이터베이스 같은 저장소가 필요합니다. API 응답은 상대에게 보낼 모양이고 DB 저장은 나중에도 찾을 기록이라는 역할입니다. 응답을 보냈다고 자동으로 DB에 저장되지는 않습니다. 필요한 항목을 정해 기록하며 입력 원문 전체를 무조건 남기지는 않습니다.

5. 기다리는 시간과 계산하는 시간을 구별한다

낯선 말 3개눌러서 뜻 보기
지연시간

한 요청을 보내고 응답을 받기까지 걸리는 시간. latency라고 합니다.

처리량

정한 시간 동안 처리하는 작업 수. throughput이라고 합니다.

비동기 처리

완료를 기다려야 하는 작업이 있을 때 그 대기 동안 다른 작업을 진행할 수 있게 하는 처리 방식. asynchronous processing이라고 합니다.

밤에 모은 감자 기록을 한꺼번에 예측하는 것은 배치 추론, 검사 요청에 맞춰 짧은 시간 안에 답하는 것은 실시간 추론의 예입니다. 실시간이라는 말이 대기 시간이 전혀 없다는 뜻은 아닙니다. 전자는 대량 작업을 끝내는 능력이, 후자는 개별 요청의 응답 시간이 특히 중요할 수 있습니다.

다른 서버나 파일의 응답을 기다리는 입출력(I/O) 대기와, 직접 무게를 계산하는 CPU·GPU 연산은 다릅니다. 비동기 코드의 await는 기다릴 수 있는 작업이 끝날 때까지 다른 작업에 진행 기회를 주는 표현입니다. async def는 이런 함수를 정의합니다. 동시성(concurrency)은 여러 작업을 함께 진행하는 구조이고, 병렬성(parallelism)은 여러 계산을 실제로 동시에 수행하는 것입니다. 둘을 같은 뜻으로 외우지 않습니다.

async를 붙이는 것만으로 모델 계산이 빨라지지는 않습니다. 기다림 없이 오래 계산하는 함수를 비동기 경로 안에서 그대로 호출하면 다른 요청의 진행을 막을 수도 있습니다. FastAPI의 일반 def 경로도 별도의 작업 스레드에서 실행되므로, ‘동기 함수면 서버 전체가 한 요청만 처리한다’는 설명은 맞지 않습니다. 스레드는 실행 작업을 나누는 단위 정도로 이해하고 세부 설정은 수업에 남깁니다.

또 실시간 요청을 아주 잠깐 모아 여러 건을 한 번에 계산하는 배칭(batching)도 있습니다. 장치 활용이 좋아져 처리량이 늘 수 있지만, 먼저 온 요청은 묶음을 기다립니다. 야간 배치 추론과도 구별해야 합니다. 실제 효과는 모델과 장치, 요청량에 따라 달라지므로 측정 없이 ‘몇 배 빨라진다’고 정할 수 없습니다.

선택 용어 · REST — 자원을 중심으로 HTTP 메서드 등 일관된 인터페이스를 사용하는 설계 방식.

선택 용어 · gRPC — 정의한 메시지와 원격 함수 호출을 중심으로 통신하는 방식.

선택 용어 · WebSocket — 연결을 유지하며 양방향 메시지를 주고받는 통신 방식.

선택 용어 · WebRTC — 실시간 음성·영상·데이터 연결에 쓰이는 웹 기술.

REST 방식의 HTTP API에서는 자원의 경로와 메서드로 기능을 구분합니다. gRPC를 사용해도 요청과 결과의 구조를 맞춰야 한다는 문제는 남습니다. 강의 p15–16의 예에서는 WebSocket으로 연결 준비 신호를 중계하고 WebRTC로 미디어를 보냅니다. 이것이 WebSocket은 언제나 신호만 보낼 수 있다거나 WebRTC가 언제나 중계 없이 직접 연결된다는 뜻은 아닙니다. 이번 무게 요청 한 건의 구조를 이해하는 데 이 연결 구현까지 필요하지는 않습니다.

선택 용어 · MariaDB — 자료를 저장하고 조회하는 관계형 데이터베이스 시스템.

선택 용어 · SQLAlchemy — Python에서 DB와 연결하고 자료를 다루는 도구.

선택 용어 · ORM — 프로그램의 객체와 DB 테이블 사이를 연결하는 방식.

객체는 프로그램에서 값과 기능을 묶어 다루는 단위, 테이블은 행과 열로 기록을 보관하는 구조, 레코드는 보관한 한 건의 기록으로 이해하면 됩니다. Pydantic의 API 스키마와 DB 테이블 구조는 목적이 다르므로 항상 같은 항목을 가져야 하는 것은 아닙니다.
