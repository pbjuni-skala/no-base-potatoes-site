Day 02. 모델을 바꿀 때 기록하고 확인할 것

예정 강의일 · 2026.10.01

감자 무게 예측 서비스에 더 좋은 모델을 넣으려고 합니다. 개발자가 파일 하나를 건넸지만, 어떤 자료로 만들었고 무엇과 비교했는지 모르면 교체해도 되는지 판단하기 어렵습니다. 개발자의 컴퓨터에서 잘 읽히던 파일이 서버에서도 읽힌다는 보장도 없습니다.

오늘은 실험 기록에서 모델 버전을 찾고, 실행 환경을 준비해 검사한 뒤 서비스에 반영하는 흐름을 배웁니다. 예습에서는 각 도구가 맡는 역할과 검사 사이의 관계를 읽습니다. 설치·학습·실제 배포는 수업에서 다루며 아래 수치와 기록은 설명용 합성 예시입니다.

지난 수업 복습

Day 1의 서비스는 다른 프로그램의 요청을 받아 입력 조건을 검사하고, 학습 때와 같은 전처리를 거쳐 모델의 예측을 응답했습니다. API는 이 요청과 응답의 약속입니다. 모델 파일을 갖고 있는 것과 요청에 응답할 수 있는 서버를 운영하는 것은 다릅니다.

이번 과목의 합성 배치 P-0930은 먼저 얻은 영상의 표면적과 품종으로 무게를 추정하고, 저울 실측은 나중 평가에 쓰는 설명 상황입니다. 이전 과목 P-0928의 재검수 분류와 다른 회귀, 즉 숫자를 예측하는 문제입니다. 입력은 surface_area_cm2(표면적)와 variety(품종), 출력은 predicted_weight_g(예측 무게)입니다. 실제 weight_g는 입력에 넣지 않습니다. 응답의 model_version은 사용한 모델, request_id는 어느 요청의 결과인지를 구별합니다.

오늘 수업에서 꼭 가져가야 할 것

모델을 바꿀 때 무엇을 함께 기록하고 검사해야 같은 서비스를 다시 만들 수 있을까요?

모델 파일에 실험의 조건과 평가 결과를 연결하고, 어떤 버전을 쓸지 선택합니다. 그 모델을 읽을 코드와 실행 환경도 함께 맞춘 뒤, 입력 조건과 예측 성능을 검사합니다. 마지막으로 서버가 선택한 버전을 실제로 불러와 응답하는지 확인해야 교체가 이어집니다.

1. 모델이 만들어진 과정도 서비스의 일부다

DevOps

MLOps

머신러닝의 데이터 준비·학습·평가·배포·모니터링을 연결해 관리하는 원칙과 실천.

파이프라인

앞 단계의 결과가 다음 단계의 입력으로 이어지도록 구성한 처리 흐름. pipeline이라고 합니다.

감자 서비스의 코드가 같아도 새로 모은 데이터로 학습하면 모델이 달라질 수 있습니다. 전처리가 달라져도 같은 표면적 숫자를 다르게 해석할 수 있습니다. 그래서 MLOps는 코드에 더해 데이터, 학습 설정, 모델 파일, 평가 기록의 연결을 중요하게 다룹니다. 일반 소프트웨어도 환경과 설정이 필요하므로 DevOps를 ‘코드만 관리하는 일’로 단정하지는 않습니다.

데이터 준비 → 학습과 기록 → 평가 → 버전 관리와 배포 → 운영 관찰

이것이 모델의 수명주기, 즉 만들어져 쓰이고 바뀌는 전체 과정입니다. 운영에서 새 문제가 발견되면 데이터와 학습 단계로 돌아올 수 있습니다. Day 2는 기록과 배포에, Day 3는 운영 관찰과 대응에 집중하지만 MLOps의 범위에는 모니터링도 포함됩니다. 날짜별 수업 구분이 기술 영역의 경계를 뜻하지는 않습니다.

재현성

어떤 조건으로 결과를 만들었는지 남겨 다시 확인할 수 있게 하는 성질. reproducibility라고 합니다.

‘P-0930 자료로 학습했다’는 설명만으로는 부족합니다. 어느 시점에 보관한 데이터인지, 어떤 전처리·설정·코드·실행 환경을 썼는지 알아야 차이를 조사할 수 있습니다. 조건을 기록하면 재현을 돕지만, 기록 도구를 사용했다는 사실만으로 모든 환경에서 똑같은 숫자가 보장되지는 않습니다.

2. 실험 추적은 점수에 만든 과정을 붙인다

낯선 말 3개눌러서 뜻 보기
실험 추적

학습 실행의 설정, 평가 지표와 결과 파일을 연결해 기록하는 일. Experiment Tracking이라고 합니다.

아티팩트

학습이나 평가에서 만들어 보관하는 파일 등의 산출물. artifact라고 합니다.

메타데이터

자료나 산출물이 무엇이며 어떻게 만들어졌는지 설명하는 정보. metadata라고 합니다.

강의에서 사용하는 MLflow는 이런 기록과 모델 관리를 돕는 도구입니다. 한 학습 실행을 run이라고 하고, 관련 실행들을 실험(experiment)으로 묶어 볼 수 있습니다. 감자 모델에서 설정을 바꾸어 두 번 학습했다면 각각의 실행 기록이 필요합니다.

옆으로 밀어서 비교 →
실험 기록의 종류감자 모델에서 남길 예나중에 답할 질문
설정값사용한 입력 항목, 트리 깊이 등 학습 조건무엇을 바꾸었는가?
지표같은 평가 자료에서 측정한 RMSE그 변화로 평가가 어떻게 달라졌는가?
아티팩트모델 파일과 전처리 파일실제로 불러올 결과물은 어디에 있는가?
메타데이터코드·데이터 버전, 실행 시점, 평가 자료의 구분이 결과를 어떤 조건에서 만들었는가?

점수만 적으면 서로 다른 자료에서 나온 결과를 같은 조건의 비교로 오해할 수 있습니다. 파일만 남기면 어느 실험의 좋은 결과였는지 잊기 쉽습니다. 점수와 조건과 파일을 한 실행으로 연결하는 것이 핵심입니다. 기록된 설정값은 실험에 전달한 조건이며, 모델이 학습 중 알아낸 모든 내부 값을 뜻하지는 않습니다.

3. 버전을 등록하는 일과 서버가 읽는 일은 다르다

낯선 말 2개눌러서 뜻 보기
모델 레지스트리

이름이 붙은 모델의 버전과 관련 정보를 관리하는 목록·저장 체계. Model Registry라고 합니다.

모델 버전

서로 구별되는 모델 결과물에 붙이는 식별값. model version이라고 합니다.

실험 추적이 ‘무엇을 해 봤는가’의 기록이라면, 레지스트리는 ‘어떤 모델 결과물을 관리하고 사용할 것인가’를 연결합니다. P-0930 무게 모델의 v1과 v2를 등록하면 각 버전이 어느 실험과 파일에서 왔는지 찾아갈 수 있어야 합니다. 등록됐다고 자동으로 더 좋은 모델이거나 운영 중인 모델은 아닙니다.

운영에 쓸 v2를 고르는 일을 승격(promotion)이라고 부를 수 있습니다. 선택을 표시하는 별칭(alias)을 쓰기도 합니다. 그러나 레지스트리의 운영 대상 표시를 바꿔도, 실행 중인 서버 메모리에 남은 v1이 저절로 v2가 되는 것은 아닙니다.

v2 등록 → 평가를 근거로 운영 대상 선택 → 서버에서 v2 로딩 → 실제 응답 버전 확인

로딩은 모델 파일을 읽어 예측에 사용할 수 있게 준비하는 일입니다. 서버 시작 때 모델을 읽도록 구성했다면 새 선택을 적용하는 재시작이나 재배포가 필요합니다. 이미 읽은 모델을 바꾸는 별도 기능이 있다면 그 기능의 성공도 확인해야 합니다. 응답의 model_version에는 단순히 선택 목록을 다시 읽은 값이 아니라 그 예측에 실제로 사용한 모델 버전이 담겨야 변경 여부를 추적할 수 있습니다.

낯선 말 1개눌러서 뜻 보기
롤백

문제가 생긴 변경을 되돌려 이전에 확인한 버전으로 복구하는 일. rollback이라고 합니다.

v2를 읽지 못하거나 교체 뒤 오류가 늘면 이전 버전으로 돌아갈 수 있어야 합니다. 이를 위해 v1 파일뿐 아니라 그 모델과 맞는 전처리·코드·환경 정보를 보존합니다. 이전 버전으로 돌아가는 일 역시 선택 표시 변경과 실제 서버 반영을 모두 확인해야 합니다.

4. 이미지는 실행할 재료이고 컨테이너는 실행 중인 상태다

낯선 말 4개눌러서 뜻 보기
의존성

프로그램이 동작하는 데 함께 필요한 다른 프로그램이나 라이브러리. dependency라고 합니다.

Dockerfile

실행 환경의 바탕, 설치할 의존성, 넣을 파일과 시작 방법을 적은 이미지 제작 지침 파일.

이미지

프로그램 실행에 필요한 파일과 환경을 묶어 둔 패키지. 여기서는 Docker image를 뜻합니다.

컨테이너

이미지를 바탕으로 격리된 환경에서 실행하는 프로그램과 그 실행 상태. 실행 중인 프로그램을 프로세스(process)라고 하며, 컨테이너는 영어로 container라고 합니다.

감자 서버는 API 코드 외에도 모델 파일을 읽는 라이브러리 등이 필요합니다. 개발 환경과 서버의 라이브러리 버전이 다르면 파일을 읽지 못하거나 동작이 달라질 수 있습니다. Docker는 실행 환경을 이미지로 만들고 그 이미지로 컨테이너를 실행하도록 돕습니다. Dockerfile을 따라 이미지를 만드는 과정을 빌드(build)라고 합니다.

Dockerfile과 필요한 파일 → 이미지 빌드 → 컨테이너 실행 → 요청에 응답

같은 이미지로 여러 컨테이너를 실행할 수 있습니다. 이미지를 새로 만들었다고 이미 실행 중인 컨테이너가 자동 교체되지는 않습니다. 또한 모델 파일을 이미지에 넣을 수도 있고 실행할 때 외부 레지스트리에서 읽을 수도 있습니다. 후자의 경우 이미지가 같아도 선택한 모델 버전이 달라질 수 있습니다.

이미지로 코드와 의존성 차이를 줄여도 외부 모델·데이터·설정이나 장비 차이까지 모두 사라지는 것은 아닙니다. 따라서 ‘컨테이너를 썼으니 RMSE도 반드시 같다’고 판단하지 않고, 입력과 모델·전처리 조건 및 실제 결과를 다시 확인합니다.

5. 같은 이미지도 실행할 때의 연결 설정이 필요하다

낯선 말 2개눌러서 뜻 보기
환경변수

프로그램 실행 환경에서 이름과 값으로 전달하는 설정. environment variable이라고 합니다.

포트

한 컴퓨터의 네트워크 연결에서 어느 프로그램의 통신 지점인지 구분하는 번호. port라고 합니다.

감자 서버가 어느 모델 관리 서버를 찾을지 주소를 환경변수로 전달할 수 있습니다. 이미지 속 코드가 같아도 주소 설정이 다른 모델 저장소를 가리키면 다른 모델을 읽을 수 있습니다. 코드·모델·환경 설정을 함께 기록해야 하는 이유입니다.

컨테이너 안의 서버가 8000번 포트에서 기다린다고 해도 컴퓨터 밖 요청이 바로 닿는다고 가정하지 않습니다. 예를 들어 9000:8000이라는 포트 연결 표기는 바깥 컴퓨터의 9000번으로 온 요청을 컨테이너의 8000번에 연결한다는 뜻입니다. 호출할 주소의 번호와 서버가 내부에서 기다리는 번호를 구분해야 합니다.

Docker Compose는 서빙 앱과 모델 관리 서버처럼 여러 서비스를 한 설정으로 정의하고 실행하도록 돕는 도구입니다. 함께 실행한다고 서로의 주소나 준비 상태가 자동으로 맞는 것은 아닙니다. 상대 서비스가 실제로 준비됐는지와 주소 연결도 확인해야 합니다. 여기서는 배포 명령보다 무엇을 어디에 연결하는 설정인가를 읽으면 됩니다.

6. 새 버전이 나아졌는지는 같은 자료와 단위로 확인한다

낯선 말 1개눌러서 뜻 보기
RMSE

예측 오차를 제곱해 평균낸 뒤 제곱근을 구한 값. 평균제곱근오차(Root Mean Squared Error)라고 합니다.

실제 무게가 100g·200g인 두 감자에 103g·204g을 예측했다면 오차 크기는 3g·4g입니다. RMSE는 √((3² + 4²) / 2) ≈ 3.54g입니다. 제곱근 기호 √는 제곱하기 전 크기로 되돌리는 계산을 나타냅니다. 공식을 외우기보다 무게와 같은 g 단위로 읽으며, 큰 오차에 더 민감하다는 점을 잡으면 됩니다. 단순 오차 크기 평균인 3.5g과 계산 방법이 다르고, ‘정답률 3.54%’도 아닙니다.

v1과 v2를 비교할 때는 각각 학습에 쓰지 않은 같은 평가 자료와 입력 조건으로 계산합니다. 평가 자료가 바뀌었다면 과거에 적어 둔 v1 점수만 가져오지 않고 두 모델을 같은 조건에서 다시 평가해야 합니다. 후보를 반복해서 고르는 자료와 마지막 확인 자료의 역할도 구분합니다.

강의의 HAIC 예시는 다음 날 주가를 예측하므로 미래 자료가 과거를 예측하는 학습에 들어가지 않게 시간 순서도 지켜야 합니다. 강의의 RMSE 4달러 기준은 그 주가 사례의 조건이며, 감자 무게의 g 기준으로 그대로 옮길 수 없습니다.

낯선 말 1개눌러서 뜻 보기
성능 회귀 테스트

변경한 뒤 성능이 이전보다 허용 범위를 넘어 나빠졌는지 확인하는 검사. performance regression test라고 합니다.

숫자를 예측하는 ‘회귀 모델’의 회귀와, 변경 뒤 악화를 찾는 ‘회귀 테스트’의 회귀는 문맥이 다릅니다. 감자 모델에서는 오차의 절대 기준뿐 아니라 기존 모델보다 나빠졌는지도 확인할 수 있습니다. 허용 오차와 악화 허용 폭은 서비스 목적에 맞춰 미리 정할 값이며, 새 모델이 통과하도록 결과를 본 뒤 바꾸는 기준이 아닙니다.

7. 자동화는 검사를 연결하고 실패한 교체를 멈춘다

낯선 말 2개눌러서 뜻 보기
CI/CD

변경을 지속적으로 통합·검사하고 배포 가능한 상태로 준비하거나 배포까지 연결하는 방식. Continuous Integration과 Continuous Delivery 또는 Deployment의 약자입니다.

게이트

다음 단계로 넘어가기 전에 정한 조건의 통과 여부를 확인하는 지점. gate라고 합니다.

모델 개발의 파이프라인에서는 데이터 입력 조건 검사, 같은 조건의 모델 평가, 이미지 제작과 서버 응답 확인을 연결할 수 있습니다. 입력 숫자의 형식이 맞아도 표면적의 단위가 학습 때와 다르면 잘못된 예측을 할 수 있으므로 전처리와 단위의 일치도 봅니다. RMSE만 좋다고 서버의 입력 처리나 모델 로딩이 성공한다는 뜻은 아닙니다.

예를 들어 설명용 게이트를 ‘평가 RMSE 10g 이하이며 기존 모델보다 나빠지지 않음’으로 정했다고 합시다. 10g은 임의의 감자 예시이지 실제 품질 기준이나 강의의 4달러와 같은 기준이 아닙니다. 후보가 9g이어도 같은 평가에서 기존 버전이 8g이었다면 이 예시의 두 번째 조건을 통과하지 못합니다.

평가 실패 시 교체를 멈추고 기존 버전을 유지하도록 설계합니다. 평가를 통과해도 새 컨테이너가 모델을 읽지 못할 수 있으므로 실제 응답과 버전을 확인하고, 실패하면 교체를 보류하거나 확인된 버전으로 복구합니다. 검사 자동화는 정한 조건을 반복 확인하는 장치이며 앞으로의 품질을 보장하는 증명은 아닙니다. 그래서 다음 날에는 운영에서 무엇을 기록하고 어떻게 변화를 알아챌지 이어서 봅니다.

더 살펴보기: 같은 레지스트리라는 말의 대상

선택 용어 · 이미지 레지스트리 — 컨테이너 이미지를 저장하고 배포할 수 있도록 제공하는 저장소. image registry라고 합니다.

모델 레지스트리는 모델 버전과 실험의 연결을 관리하고, 이미지 레지스트리는 실행 패키지인 이미지를 저장합니다. 감자 모델 v2를 등록한 것과 서빙 앱 이미지를 저장한 것은 다른 사건입니다. 모델 파일을 이미지에 포함해도 두 버전의 연결은 남겨야 하며, 이미지 태그와 모델 버전이 우연히 같은 숫자라고 동일한 대상이 되지는 않습니다.

선택 용어 · Stage — 모델 버전에 Staging·Production 같은 단계를 표시하던 MLflow의 관리 기능.

강의 화면에는 모델의 Staging·Production 같은 Stage가 나옵니다. MLflow 공식 문서는 Stage를 2.9부터 사용 중단 예정 기능으로 안내하고 별칭 등으로 이전하는 방향을 제시합니다. 수업에서 설치한 버전의 방식은 별도로 확인하되, 예습에서는 버전을 식별하고 운영 대상을 선택한 뒤 실제 서버에 반영한다는 관계를 유지하면 됩니다.
